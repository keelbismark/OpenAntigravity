## Частично закрыто

### P0 — `connection refused` как класс

Исходная жалоба: `dial tcp 127.65.71.1:443: connect: connection refused`.

Замер семантики 10061 на Windows:

| Состояние двери | Клиент видит |
|---|---|
| никто не слушает | **10061 connection refused** |
| приняла и закрыла | 10053 connection aborted |
| прочитала и закрыла | 10054 forcibly closed |

⇒ 10061 возможен только при отсутствии слушателя. v1.5.1–1.5.9 убрали
доминирующие причины исчезновения релея и рассогласования DNS/двери; в
финальном прогоне дверь работала (`Гейт-хосты через локальные адреса: да`,
`Сокеты службы: Tunnel`).

**Остаток:** дверь по-прежнему живёт внутри процесса релея, а DNS-ответ имеет
`ANSWER_TTL = 30 с`. Теоретическое окно между перезапуском релея и истечением
кэша остаётся. Полное закрытие — этап 2 ниже.

**Этап 2 (если понадобится):**
1. дверь — владелец `127.65.71.1:443` в процессе, который не перезапускается
   вместе с релеем (watchdog-задача или `door.exe`), со своим мьютексом;
2. дверь ↔ прокси через **named pipe** вместо TCP-порта;
3. TTL → 5 с + постоянный hosts-pinning (`src/network/hosts.rs`);
4. нагрузочный тест: 20 перезапусков релея при живом кэше — ни одного 10061.

**Файлы:** `src/network/loopback.rs`, `src/network/dns_forwarder/mod.rs`,
`src/network/hosts.rs`, `src/platform/relay_role.rs`, `src/network/proxy/mod.rs`.

### P0 — причина залипания тёплого прохода

v1.5.1 закрыл следствие (heartbeat 5 мин, роль освобождается, standby
подхватывает). Причина, по которой `warm_forever` перестал ходить, **не
установлена**. Кандидаты: PowerShell-проверка VPN (`dns_forwarder/mod.rs:616`),
`resolvers::warm` (стр. 701), `proxy::probe_direct`/`probe_relay`
(стр. 711–741), блокировка на `gate::update()` → `fs::rename`.

**Решение:** per-step таймауты, лог с именем зависшего шага, watchdog внутри
потока. **Критерий:** при искусственной блокировке шага проход возвращается
за ≤ N с, лог называет шаг.

## Осталось открытым

### P1 — честная диагностика `WSAEACCES` при bind

Релей писал «доступ запрещён — антивирус или брандмауэр» (os error 10013),
когда `TgWsProxy_windows` держал `0.0.0.0:53129`. `portcheck::diagnose_on()`
смотрит только таблицу LISTENER, не находит держателя и называет это `Cause::Denied`.

**Важно:** гипотеза «дело в bound-but-not-listening сокете» **опровергнута
замером**: такой сокет не появляется в extended TCP table и не мешает bind'у.
Изменение откачено — не повторять.

Нужно выяснить реальный источник 10013 (WFP-фильтр / эксклюзивная привязка /
резервирование), не гадать. **Файлы:** `src/platform/portcheck.rs`,
`src/network/proxy/mod.rs`.

### P1 — подтверждение portable-переработки на живой машине

Проверено пробным запуском из свежей папки с `portable.flag`. DESKTOP-сборка
проверена в финальном прогоне v1.5.9. Отдельно стоит проверить:
`signature gone, left untouched … out\main.js` — ожидаемое поведение при
обновлении IDE, не «починить» слепым перепатчиванием.

### P2 — диагностика одним вопросом

Расширить `--relay-role` (`taken`/`busy`) до `--relay-status`: владелец роли,
порт прокси, свежесть записи, держатели адресов. **Файлы:** `relay_role.rs`,
`main.rs`, `gate.rs`.

### P2 — in-process путь как основной

Аналоги (`yuaotian/antigravity-proxy`, `dinobot22/antigravity-ssh-proxy`)
не держат дверь: перехватывают `connect()`/`getaddrinfo()` в клиенте.
У OpenAntigravity есть эквивалент — `OAG_GATEWAY` + патч бинаря
(`src/patcher/binary.rs::patch_proxy_var`). Сделать его основным путём,
перезапускать `language_server` при смене состояния (паттерн ssh-proxy
`src/extension.ts:103`); дверь — фолбэк. Тогда клиент не зависит от DNS-кэша.

## Приложение: воспроизведение ключевых замеров

```
# семантика ошибки
bind 127.65.71.9:443 и сразу connect → 10061

# отравленная запись о порте (главный тест watchdog'а)
proxy_port = 44129 при живом прокси на 53129,
OAG_GATEWAY выставлен, ждать 110 с → переменная жива

# rivalry ролей
два процесса с --relay-role → второй печатает busy;
после убийства первого роль свободна

# расхождение сборок
«Сборка службы: X (окно: Y)» в отчёте — X должен равняться Y

# источник настроек релея
«Свой прокси: адрес не прочитан из <путь>» — путь должен совпадать
с тем, куда окно пишет upstream.txt
```

Тесты: `tests/test_relay_role.rs`, `src/network/proxy/tests.rs`,
`src/network/routes/tests.rs`, `src/patcher/watchdog.rs`,
`src/core/portable.rs`, `src/patcher/ide.rs`.
