## P0 — убрать `connection refused` как класс

**Симптом (исходная жалоба):**
`Post "https://cloudcode-pa.googleapis.com/…": dial tcp 127.65.71.1:443: connect: connection refused`

**Измерение, которое всё объясняет (семантика 10061 на этой машине):**

| Состояние двери | Что видит клиент |
|---|---|
| никто не слушает | **10061 `connection refused`** |
| дверь приняла и закрылась | 10053 `connection aborted` |
| дверь прочитала и закрылась | 10054 `forcibly closed` |

⇒ 10061 возможен **только при отсутствии слушателя** в момент дозвона.

**Почему слушатель исчезает:** дверь (`src/network/loopback.rs`) живёт внутри
процесса релея, а DNS-ответ живёт отдельно — `ANSWER_TTL = 30` с. За мером:
`forwarder.log` содержал ~19 перезапусков релея (egress `if8 → if9 → if11 → if12`),
после чего процесс исчезал; клиент с закэшированным адресом звонил
в пустоту. v1.5.1 уменьшает частоту, но **не убирает окно**.

**Решение (этап 2):**

1. **Дверь переживает релей.** Владельцем адреса `127.65.71.1:443` становится
   процесс, который не перезапускается вместе с релеем (watchdog-задача или
   отдельный `door.exe`), с собственным именованным мьютексом.
2. **Дверь ↔ прокси через named pipe**, а не через TCP-порт: порт плавает
   (53129/43129/запасные), труба переживает его переезд и мгновенно видит
   смерть прокси вместо `connect_timeout(3s)`.
3. **DNS-ответ не переживает дверь**: TTL → 5 с как страховка + постоянный
   hosts-pinning (`src/network/hosts.rs` уже умеет писать fence-блок), у
   `hosts` нет TTL.
4. Нагрузочный тест: убить/перезапустить релей, пока клиент держит кэш, —
   `connect()` к 127.65.71.1:443 не должен дать 10061.

**Файлы:** `src/network/loopback.rs`, `src/network/dns_forwarder/mod.rs`,
`src/network/hosts.rs`, `src/platform/relay_role.rs`, `src/network/proxy/mod.rs`.

**Критерий приёмки:** в цикле «перезапустить релей 20 раз» ни одного 10061;
само-пробы двери из соседнего процесса всё время успешны.

## P0 — найти причину залипания тёплого прохода

**Симптом:** 2026-11-16, `forwarder.log` замолчал на 11:49:35; процесс
продолжал жить и держать порты до ~12:0x, где исчез. Установленный релей молчал
с 10:20:47, `gate.json` застыл в 10:21:18.

**Что сделано:** v1.5.1 закрывает *следствие* — heartbeat (`HEARTBEAT_STALE_AFTER
= 5 min`) завершает процесс, роль освобождается, standby подхватывает.

**Что не сделано:** причина, по которой `warm_forever` перестал ходить,
неизвестна. Кандидаты (нужно измерить, а не гадать):

- PowerShell-проверка VPN в начале прохода (`dns_forwarder/mod.rs:616`);
- `resolvers::warm(dns::core_namespaces(), egress)` (стр. 644);
- `proxy::probe_direct(egress)` / `probe_relay()` (стр. 654-681);
- блокировка на `gate::update()` → `fs::rename` общего `gate.json`.

**Решение:** per-step таймауты, запись в лог о том, какой шаг завис, и
watchdog **внутри** потока (не только на уровне процесса).

**Критерий приёмки:** при искусственной блокировке любого шага проход
возвращается за ≤ N секунд, лог называет шаг, релей остаётся владельцем роли.

## P1 — семантика тумблеров `dns` / `local_proxy`

**Симптом (измерен):** `data\settings.json` был переписан в 11:51:18 с
`"local_proxy": false, "dns": false`. Причина в коде — `apply.rs:705-713`:
при чужом `HTTPS_PROXY` в системе программа отказывается ставить свой
переменный и **пишет `local_proxy = false`**, а `loopback::active()`
(`src/network/loopback.rs:80`) требует этот же флаг. ⇒ Дверь выключается
вместе с переменной, хотя это разные механизмы: дверь не нуждается в env var,
ей нужен только работающий локальный прокси.

**Решение:** разделить «устанавливать переменную окружения» и «маршрут через
локальный шлюз включён». Переключатель не должен самопроизвольно уходить в
false без объяснения; карточка должна говорить: *«ваш локальный прокси
выключен: в системе задан чужой прокси …»*, с действием «всё равно использовать
наш».

**Файлы:** `src/core/ops/apply.rs`, `src/core/settings.rs`,
`src/network/loopback.rs`, `src/gui/main_view/sections.rs`.

**Критерий приёмки:** при наличии чужого `HTTPS_PROXY` дверь продолжает
подменять адрес; исчезновение переменной не выключает обход.

## P1 — честная диагностика `WSAEACCES` при bind

**Симптом (измерен):** релей написал
`не занять 127.0.0.1:53129 … (os error 10013) (доступ запрещён — антивирус
или брандмауэр)`, в то время как `TgWsProxy_windows` держал `0.0.0.0:53129`
(подключения на 149.154.167.220:443). `portcheck::diagnose_on()` смотрит только
таблицу LISTENER, не находит держателя и.call'ывает `Cause::Denied`.

**Важно:** гипотеза «дело в сокете, который только bound, не listen» была
**проверена и опровергнута** замером: такой сокет не появляется в extended TCP
table и не мешает bind'у `127.0.0.1`. Изменение откачено. Не повторять.

**Решение:** выяснить реальный источник 10013 (WFP-фильтр / эксклюзивная
привязка / изменившийся reservation), не гадать. Возможно, использовать
`GetExtendedTcpTable` с другим class + ООИ-фильтры, либо отдельный диагностический
helper, который делает bind от лица релея.

**Файлы:** `src/platform/portcheck.rs`, `src/network/proxy/mod.rs`.

**Критерий приёмки:** на машине с чужим держателем порта карточка называет
держателя или exclusion range, а не «антивирус».

## P2 — in-process путь как основной

Оба аналога (`yuaotian/antigravity-proxy`, `dinobot22/antigravity-ssh-proxy`)
не держат дверь вообще: перехватывают `connect()`/`getaddrinfo()` в процессе
клиента (MinHook / mgraftcp+LD_PRELOAD). У OpenAntigravity уже есть эквивалент —
`OAG_GATEWAY` + патч бинаря (`src/patcher/binary.rs::patch_proxy_var`).

**Направление:** сделать его основным путём; при смене состояния обхода
перезапускать `language_server` (паттерн `src/extension.ts:103` в ssh-proxy),
чтобы он подхватил переменную. Дверь остаётся фолбэком на время перезапуска.
Тогда клиент вообще не зависит от DNS-кэша.

## Приложение: как воспроизводить ключевые замеры

```
# семантика ошибки (MODE B — порт свободен)
bind 127.65.71.9:443 и сразу connect → 10061

# отравленная запись о порте (главный тест watchdog'а)
записать proxy_port = 44129 при живом прокси на 53129,
выставить OAG_GATEWAY, ждать 110 с → переменная жива, строки «снята» нет

# rivalry ролей
два процесса с --relay-role → второй печатает busy
после убийства первого роль свободна
```

Все проверки уже оформлены тестами: `tests/test_relay_role.rs`,
`src/network/proxy/tests.rs`, `src/patcher/watchdog.rs`,
`src/core/portable.rs`, `src/patcher/ide.rs`.
